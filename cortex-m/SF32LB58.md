## A. Board and populated memory

The catalogue match is **SF32LB58-DevKit-LCD-N16R32N1**, with **SF32LB58-MOD-N16R32N1**, normally **SF32LB586VDD36**. It has **16 MiB external NOR + two 16 MiB SiP HPI pSRAM devices + 1 MiB SiP NOR**. Thus N1 is NOR, not 1 Gbit NAND; A128R32N1 is the separate 128 MiB NAND module, and E4R32N1 the 4 GB eMMC module. Sources: MOD PDF p7; `W/source/en/board/devkit_guide.md:132`; `S/customer/boards/sf32lb58-lcd_n16r32n1_qspi/doc/index.md:2`.
Check the full carrier/module markings and PCB version: the SDK also names a Core N16R32N1 board (`S/build_config_gcc.yaml:45`). The LCD guide inconsistently calls its initial V1.0.0 chip 587VEE56, while its module section and V1.0.1 say 586VDD36; 587 actually denotes 32+32 MiB pSRAM and 4 MiB boot NOR. Actual user revision is **unverified**; use markings/capacity readback, not that contradictory sentence. Sources: `W/source/en/board/sf32lb58x/SF32LB58-DevKit-LCD.md:5`, `:17`, `:28`; `W/source/en/silicon/芯片型号指南.md:117`.

HCPU mappings below distinguish populated bytes from controller windows. Sources for addresses: UM Tables 1-1 and 1-4, PDF pp17,22; `S/drivers/cmsis/sf32lb58x/mem_map.h:149`, `:161`, `:230`. Capacities/ports: chip guide above, BSP `hcpu/board.conf:25` and `ptab.yaml:8` under the QSPI board directory. Speeds: LCD Wiki `:50`; DS PDF p5; UM PDF p16.

| Memory | Port; populated address ranges (inclusive) | Controller window; interface/clock |
| --- | --- | --- |
| SiP pSRAM 0, 16 MiB | MPI1: `60000000–60FFFFFF`; HCPU code alias `10000000–10FFFFFF` | 32 MiB per alias; x16 HPI DDR, 144 MHz |
| SiP pSRAM 1, 16 MiB | MPI2: `62000000–62FFFFFF`; code alias `12000000–12FFFFFF` | 32 MiB per alias; x16 HPI DDR, 144 MHz |
| External NOR, 16 MiB | MPI4: `18000000–18FFFFFF`; system alias `68000000–68FFFFFF` | 64 MiB code window; system aperture can extend to `9FFFFFFF`; QSPI x4 STR, board specifies 72 MHz |
| SiP boot NOR, 1 MiB | MPI5: `1C000000–1C0FFFFF` | 64 MiB window; QSPI x4, 48 MHz; controller supports DTR, actual boot transaction mode **unverified** |

**The 32 MiB pSRAM is not contiguous in this map.** Each device occupies half its 32 MiB aperture; the intervening `61000000–61FFFFFF` is not another 16 MiB of physical RAM. Aliases do not add capacity. SDK `PSRAM_SIZE` describes the first bank only (`mem_map.h:230`); reserve/manage both banks explicitly. Any remapping that would join them is **unverified**, not assumed in E.

LCD carrier connectors: 30-pin two-lane DSI FPC, 40-pin DPI/RGB FPC, and 40-pin SPI/DSPI/QSPI header; touch is I²C. These are alternatives, not evidence of the user's fitted panel. Sources: LCD Wiki `:60`, `:562`; exact SDK selections below.

## B. HCPU, execution and cache policy

Same Rust target/FPU choice as [S §B](SF32LB52.md#b-core-memory-and-generated-code): `thumbv8m.main-none-eabihf`, matching the C hard-float ABI; SF58 UM PDF p4 confirms single-precision FPU. HCPU remains up to 240 MHz, selected by this BSP; **D-cache grows to 32 KiB**, matching the 32 KiB I-cache (4-way D, 2-way I). Sources: DS PDF p4; `S/customer/boards/sf32lb58-lcd_base/bsp_init.c:114`.

| HCPU SRAM | Range; usable interpretation | Source |
| --- | --- | --- |
| 64 KiB ITCM | `00010000–0001FFFF`, HCPU-only, zero wait | UM PDF p16 |
| 64 KiB retention SRAM | `00020000–0002FFFF`, maximum 120 MHz | UM PDF p16 |
| 2048 KiB main SRAM | `20000000–201FFFFF`, zero wait up to 240 MHz; first 128 KiB is also DTCM, not extra RAM | UM PDF p16 |

Total is **2176 KiB = 2.125 MiB**, not one contiguous buffer. ACPU has separate 512 KiB at `20200000–2027FFFF`; LCPU has 1056 KiB and up to 96 MHz. Neither is counted as free HCPU heap here; the HCPU SDK also reserves ROM data/mailboxes. Sources: DS PDF p4; UM PDF p16; `S/drivers/cmsis/sf32lb58x/mem_map.h:302`.
**pSRAM execution is permitted.** HCPU MPU makes `60000000–63FFFFFF` normal, RW, executable, WB with this board's `PSRAM_CACHE_WB`; code aliases `10000000–1FFFFFFF` are RO executable. Thus publish through one writable system alias, avoiding incoherent alias use. Sources: `S/drivers/cmsis/sf32lb58x/Templates/system_bf0_ap.c:174`, `:189`; QSPI board `hcpu/board.conf:33`. Hardware generate/execute/overwrite behavior remains **unverified**.
Cache maintenance by address is the **same shared `core_mstar.h` implementation** and 32-byte-line publication sequence described in [S §B](SF32LB52.md#b-core-memory-and-generated-code); SF58 includes it at `S/drivers/cmsis/sf32lb58x/register.h:323`. MPU has 12 HCPU regions. TrustZone implementation and user Secure/Non-secure state remain **unverified**, as in S: SF58 declares zero SAU regions and calls `TZ_SAU_Setup()` only under CMSE. Sources: `register.h:282`, `:318`; `system_bf0_ap.c:428`. Secure Boot support alone does not establish user security state.
LCPU need not execute emulator work: the HCPU BSP resets/halts it before memory/clock initialization; release is a separate operation. Intern proposes keeping it halted with Bluetooth disabled, retaining required LPSYS peripheral clocks for UART/GPIO; complete LPSYS power-off is **unverified** and is not implied by halting the core. Sources: `S/customer/boards/sf32lb58-lcd_base/bsp_init.c:78`, `:101`; `S/drivers/hal/bf0_hal_rcc.c:1658`. No ACPU worker is proposed.

## D. Bring-up differences

ROM still loads stage 2 into RAM, but SF58 boot metadata/loader reside on **MPI5 SiP NOR**. SDK defaults place flash table at `1C000000`, boot patch at `1C010000`, loader at `1C020000`. Sources: `S/docs/source/en/app_development/startup_flow.md:70`; `S/drivers/cmsis/sf32lb58x/mem_map.h:178`.
General startup documentation supports external NOR XIP (`startup_flow.md:130`), but **this exact BSP's `ptab.yaml` stores HCPU code at MPI4 offset 0 and executes it from MPI1 pSRAM offset 0**, reserving 4 MiB there; bank 0 data starts at +4 MiB, bank 1 supplies 16 MiB data. Do not assume NOR implies XIP. Sources: `S/customer/boards/sf32lb58-lcd_n16r32n1_qspi/ptab.yaml:14`, `:26`; DSI/DPI tables have the same entries. The firmware/partition/loader must agree before reclaiming that reservation or moving text to SRAM/NOR.
Use the SDK-generated image/address manifest and UART download scripts, or [sftool](https://github.com/OpenSiFli/sftool/blob/master/README_EN.md) with `-c SF32LB58 -m nor -p <port>` and the verified manifest addresses; do not reuse the SF52 addresses in S. Sftool supports SF58, defaults to 1,000,000 baud, and distinguishes a separate Type1 pinout mode; the user's required mode is **unverified**. Nothing was flashed or installed.
ROM download/debug UART is **USART4, PB36 RX/PB37 TX**, on the USB-UART port; install Mode jumper then power on for download, remove it for normal boot. For app logs, explicitly select and route that console; BSP also maps UART1 to PA31 TX/PA32 RX. The no-OS example retains S's 1,000,000-baud 8N1 setting. Sources: LCD Wiki `:152`, `:532`; `S/customer/boards/sf32lb58-lcd_base/bsp_pinmux.c:187`, `:339`; `S/example/get-started/blink/no-os/src/main.c:100`.
SWD moves to **PB11 SWDIO / PB7 SWCLK**, separate from that UART. Wiki documents J-Link plus the supplied adapter, GND and 3.3 V reference. Do not carry over S's SF52 probe-rs command as SF58 evidence; installed debugger support is **unverified**. Sources: LCD Wiki `:213`, `:540`.

## E. Memory fit and first measurements

The unchanged QEMU layout is not a board image; see [S §E](SF32LB52.md#e-memory-fit-and-first-measurements). Retain its ~5.8125 MiB JIT estimate and Lead's ~0.7 MB firmware estimate (linked sizes **unverified**). A packed port with text in SRAM/NOR has `32 − 16 − 5.8125 = 10.1875 MiB` pSRAM left before other runtime costs. Keeping the SDK's 4 MiB pSRAM code reservation reduces that to **6.1875 MiB**, not merely by the actual text size. Sources: S §E; partition table in D.
Use HCPU SRAM for firmware/hot state/stacks; do not add 2.125 MiB to a contiguous pSRAM guest allocation or count shared DTCM twice. ~0.7 MB text is ~0.67 MiB if decimal and can fit within the 2 MiB main SRAM in principle; SDK data/stack and placement must be measured. Packing text into pSRAM instead subtracts its actual loaded size. These are calculations from B and the Lead estimate, not a linked allocation map.
For transparent comparison, the table charges VGA **separately** and reserves 2 MiB for other host/SDK/display/allocator/I/O costs. S's original 2 MiB reserve included VGA: using that convention instead gives 26.19 MiB for a reduced packed layout, provided everything fits the reserve. No VGA reduction or repartitioning was implemented here.

| Port layout | VGA; JIT | Aggregate pSRAM left after code reservation + explicit VGA + JIT + 2 MiB other reserve | Practical initial guest target |
| --- | --- | --- | --- |
| SDK default 4 MiB code reservation; current r86 allocations | 16; 5.8125 MiB | **4.19 MiB** | 4 MiB; VGA occupies the entire other bank |
| Packed code in SRAM/NOR; current r86 allocations | 16; 5.8125 MiB | **8.19 MiB** | 8 MiB |
| Packed; reduced | 0.25; 2 MiB arena + 1.8125 MiB tables | **25.94 MiB** | **16 MiB**, one bank |
| Packed; reduced | 1; 2 MiB arena + 1.8125 MiB tables | **25.19 MiB** | **16 MiB**, one bank |
| SDK default; reduced | 0.25 / 1; 3.8125 MiB | **21.94 / 21.19 MiB** | **16 MiB**, bank 1; host allocations fit bank 0's 12 MiB in this budget |

**25–26 MiB aggregate free is not a 24 MiB contiguous guest.** Current firmware passes one contiguous guest slice (`cortex-m/firmware/runtime.rs:189`); the gap in A caps one-bank guest backing at 16 MiB, even when the host fits elsewhere. More guest RAM requires a supported remap or a change to the guest-memory backing contract; both are **unverified**, outside this task. Fragmentation and SDK reservations can lower these ceilings further.
DOS/Windows 3.1 and Windows 95 memory/16-bit-engine guidance is unchanged from [S §E](SF32LB52.md#e-memory-fit-and-first-measurements); 8–16 MiB guest configurations give more room than S. Windows 98 becomes a **minimum-memory candidate only after reductions**: Microsoft's archived [KB188881](https://ftp.zx.net.nz/pub/archive/ftp.microsoft.com/MISC/KB/en-us/188/881.HTM) specifies 16 MB minimum, 24 MB recommended. No SF58 guest compatibility or speed is established, and the 24 MB recommendation does not fit a single bank.
Intern placement recommendation: use zero-wait ITCM for a measured hot subset and main SRAM for remaining hot interpreter/firmware text where it fits; retain cold text in NOR or the BSP's pSRAM load region. Compare before committing to a layout. DS PDF pp5,14 advertises pSRAM DDR144/x16 (576 MB/s interface peak) and cache-assisted XIP; external NOR here is x4 STR72 (36 MB/s calculated payload ceiling). Neither is a measured random-access or emulator rate; pSRAM code also competes with guest RAM and display traffic. JIT should remain in an explicitly executable pSRAM bank unless a measured SRAM working set fits.
The larger panel can invalidate the 2 MiB reserve: one 800×1280 RGB565/RGB888 buffer costs **1.95/2.93 MiB**, or 1024×600 costs **1.17/1.76 MiB**; double buffers double those charges. Calculated from A; DSI/DPI defaults use RGB888 (`S/customer/peripherals/display/jd9365da/jd9365da.c:63`, `htm_h070a20/htm_h070a20.c:66`). Start with a small display/buffer and measure actual allocation peaks.

First measurements are [S §E's sequence](SF32LB52.md#e-memory-fit-and-first-measurements), with these SF58 priorities proposed by Intern:

1. Read actual part/revision/clocks/boot table/MPU/security state; prove both 16 MiB banks independently, their aliases and boundaries, and exclude active firmware/SDK storage before allocating. This resolves A/B/D unknowns.
2. Prove JIT publish/overwrite with caches enabled in the chosen bank, while display/SD DMA runs; compare SRAM execution. Measure random pSRAM access and interpreter/JIT throughput for SRAM versus pSRAM versus NOR text. Interface bandwidth alone is insufficient (B/E).
3. Measure linked code, both-bank allocator peaks, stacks, JIT churn and framebuffer reservations; verify SD reads and native USB keyboard enumeration/power. Then compare interpreter/JIT on the same frozen guest media, DOS/3.1 first, Windows 95, then a 16 MiB Windows 98 experiment if the budget holds. These are proposed checks, not performed results.
