## B. Core, memory and generated code

HCPU is STAR-MC1/Cortex-M33 compatible, up to 240 MHz, DSP and single-precision FPU; LCPU is 24 MHz with 64 KiB SRAM. Use `thumbv8m.main-none-eabihf`, with a matching hard-float C ABI if linking SDK objects; this is the Rust example's configured target. Sources: DS5201 PDF p4; `R/examples/sf32lb52x/.cargo/config.toml:1`. Board-selected frequency must be measured; LILYGO documents 192 MHz in its README.

HCPU-visible map, inclusive ranges. Address windows are not populated capacities; reserved holes inside peripheral groups remain reserved. Sources: UM5201 Table 1-1, PDF pp16–18; SDK references on supplemental rows.

| Address range | Meaning |
| --- | --- |
| `00000000–0000FFFF` | 64 KiB HCPU boot ROM; not writable ITCM despite the table's HPSYS_ITCM group label |
| `10000000–11FFFFFF` / `60000000–61FFFFFF` | MPI1 32 MiB code/system-bus windows onto the same SiP NOR or pSRAM; actual chip supplies 1/4 MiB NOR or 4/8/16 MiB pSRAM |
| `12000000–1FFFFFFF` / `62000000–9FFFFFFF` | MPI2 code/system-bus windows, 224/992 MiB address space; external NOR XIP, NAND or pSRAM interface; not that much installed memory |
| `20000000–2001FFFF`; `20020000–2003FFFF`; `20040000–2007FFFF` | 128 KiB RAM0/DTCM, 128 KiB RAM1, 256 KiB RAM2 = 512 KiB HCPU SRAM; DTCM is shared SRAM, not an extra 128 KiB |
| `20400000–2040FFFF`; `20800000–2085FFFF` | LCPU SRAM and HCPU alias of its 384 KiB ROM; radio/patch/mailbox reservations mean SRAM is not a free HCPU heap. `S/drivers/cmsis/sf32lb52x/mem_map.h:50`; `S/drivers/cmsis/sf32lb52x/register.h:620` |
| `40000000…40090000` peripheral bases | LPSYS clocks, DMA, mailbox, USART, AON, GPIO and radio registers; sparse, not a contiguous RAM range. `S/drivers/cmsis/sf32lb52x/register.h:406` |
| `50000000–5003FFFF` | HPSYS APB1: clocks, LCDC, GPU, audio, security and configuration, with reserved holes |
| `50040000–5007FFFF` | HPSYS AHB1: MPI1 `50040000`, MPI2 `50042000`, SDMMC `50045000`, USB `50047000`, GFX_RAM `50050000–5005FFFF` (64 KiB); other holes reserved |
| `50080000–5009FFFF`; `500A0000–500AFFFF`; `500B0000–500BFFFF`; `500C0000–500FFFFF` | APB2 (DMA/mailbox/UART/SPI/I²C/timers), AHB2 (GPIO), APB3 (timers), APB4 (AON/PMU/RTC/watchdog), with reserved holes |
| `E0000000`, `E0001000`, `E000E000`, `E0040000` | Core ITM, DWT, system control/NVIC/MPU/cache registers, TPI bases; `S/external/CMSIS/Include/core_cm33.h:2195` |

Only HCPU uses MPI's `0x1…` aliases; DMA/display masters use `0x6…`. Prefer one `0x60000000` pSRAM mapping for heap and JIT, with explicit MPU attributes; avoid mixing aliases during writes/cache maintenance. Sources: UM5201 PDF p18 footnote; `S/drivers/cmsis/sf32lb52x/mem_map.h:101`; mapping choice is Intern's recommendation.
**pSRAM execution is supported:** the documented NAND boot copies application code there, and SDK `mpu_config()` makes `60000000–61FFFFFF` RW/executable, write-through by default or write-back with `PSRAM_CACHE_WB`. Sources: `S/docs/source/en/app_development/startup_flow.md:117`; `S/drivers/cmsis/sf32lb52x/Templates/system_bf0_ap.c:186`.
Caches: 32 KiB 2-way I-cache, 16 KiB 4-way D-cache; SDK uses 32-byte lines. SDK configures MPU, then calls `SCB_EnableDCache()` / `SCB_EnableICache()`; helpers invalidate before enabling. Sources: UM5201 PDF p15; `S/external/CMSIS/Include/core_mstar.h:31`, `:38`, `:124`; `S/drivers/cmsis/sf32lb52x/Templates/system_bf0_ap.c:129`.
JIT publish procedure: round the written interval outward to 32-byte lines, clean D-cache for the complete interval (`SCB_CleanDCache_by_Addr`, DCCMVAC), complete a DSB, invalidate I-cache for that interval (`SCB_InvalidateICache_by_Addr`, ICIMVAU), then DSB/ISB before calling it. Sources: `S/external/CMSIS/Include/core_mstar.h:95`, `:364`; `src/x86/jit/t32/arena.rs:115`. The current QEMU hook interleaves clean/invalidate and only barriers at the end; hardware publication must be reviewed against this sequence (`cortex-m/firmware/runtime.rs:72`); no firmware edits made.
MPU: present, 12 HCPU regions. TrustZone implementation/IDAU policy and the user's Secure/Non-secure state are **unverified**: SDK declares zero SAU regions and only conditionally calls `TZ_SAU_Setup()`. The inspected loader directly loads SP/PC; normal privileged execution is an inference, not a board observation. Record CONTROL, MPU/SAU identification and boot provenance before relying on privileged cache operations. Sources: `S/drivers/cmsis/sf32lb52x/register.h:233`, `:267`; `S/drivers/cmsis/sf32lb52x/Templates/system_bf0_ap.c:377`; `S/example/boot_loader/project/sf32lb520/board/main.c:46`.
Memory clocks: SiP OPI pSRAM up to DDR 144 MHz; SiP NOR recommended 96 MHz, external flash recommended 60 MHz in the silicon manual; board guides specify external QSPI NOR at 72 MHz STR. These are different documented configurations, not measured bandwidth. Exact part/timing/voltage validation is required before selecting 72 MHz. Sources: UM5201 PDF p16 §1.3.2.4–5; `W/source/en/board/sf32lb52x/SF32LB52-DevKit-Nano.md:25`; `W/source/en/board/sf32lb52x/SF32LB52-DevKit-LCD.md:30`.

## D. Bring-up procedure (documented, not executed)

ROM stage 1 starts at vector address 0, initializes boot-flash IO at the reset clock, reads the flash table and loads stage 2 into SRAM. Stage 2 initializes package pSRAM and selects NOR XIP or NAND/SD-to-pSRAM loading. The documented SF52 handoff is HCPU 144 MHz, DLL2 288 MHz, pSRAM 144 MHz, external flash 48 MHz, MPU/cache disabled. Sources: `S/docs/source/en/app_development/startup_flow.md:65`, `:117`, `:136`.
Application startup sets SP/MSPLIM, runs `SystemInit` (VTOR, FPU, MPU/cache), copies/zeros sections and enters the program; board `HAL_PreInit` selects HCPU 240 MHz and memory clocks, pinmux/power and pSRAM. These are selected BSP behavior, not a guarantee about an arbitrary preinstalled bootloader. Sources: `S/drivers/cmsis/sf32lb52x/Templates/gcc/startup_bf0_hcpu.S:165`; `S/drivers/cmsis/sf32lb52x/Templates/system_bf0_ap.c:355`; `S/customer/boards/sf32lb52-lcd_base/bsp_init.c:103`, `:154`.
Future build: in the SDK's no-OS example project, choose the identified board using `sdk.py menuconfig --board=<board>` and `scons --board=<board> -j8`; output includes binaries and UART download scripts. For Rust use Cargo's `thumbv8m.main-none-eabihf` target and a board-specific memory script. Preserve the loader or build the correct replacement; a flash table must describe the new application's length. Sources: `S/example/get-started/blink/no-os/README_EN.md:50`; `S/docs/source/en/quickstart/build.md:7`; `R/docs/flash_and_debug.md:7`; `R/examples/sf32lb52x/memory.x:1`.
Example **only for MPI2 NOR layout**: `sftool -c SF32LB52 -p <port> write_flash bootloader.bin@0x12010000 app.bin@0x12020000 ftab.bin@0x12000000`. Do not reuse these addresses for SiP NOR/NAND without its flash table. The Rust guide provides this three-image layout and permits later app-only updates if the recorded size suffices (`R/docs/flash_and_debug.md:7`, `:22`, `:35`). No flashing authorized/performed in task S.
Logs: USB-UART, normally 1,000,000 baud in the SDK no-OS example; board-specific RTS/power-reset behavior matters. Debug uses PA18 SWDIO / PA19 SWCLK (shared with UART) or SiFli UART debug. The consulted Rust guide documents `SIFLI_UART_DEBUG=1 probe-rs attach --chip SF32LB52 <elf>` with RTT and marks flashing via probe-rs unsupported; current tool/board behavior **unverified**. Sources: `S/example/get-started/blink/no-os/src/main.c:108`; `W/source/en/board/sf32lb52x/SF32LB52-DevKit-Nano.md:74`, `:103`; `R/docs/flash_and_debug.md:80`. Rust startup must handle inherited MSPLIM (`R/sifli-hal/README.md:310`).

## E. Memory fit and first measurements

Lead estimates about 0.7 MB of firmware code (`tmp/t32/task-sf32.txt:40`); no build was run to remeasure it. NOR XIP avoids charging that text to pSRAM; NAND/SD boot adds the loaded image to RAM (startup source cited in D). The QEMU image is not a board layout: it reserves a 64 MiB heap, 8 MiB code region, 128 MiB guest and 16 MiB profiling area (`cortex-m/firmware/abi.rs:7`; `r86chip/firmware/machine_abi.rs:16`).
Current JIT estimate on 32-bit ARM without profiling: 4 MiB arena + ~1.5 MiB block records (32,768 × expected 48-byte record; compiled layout **unverified**) + 128 KiB dispatch + 128 KiB page pointers + 32 KiB heat + up to 32 KiB filled indices = **~5.81 MiB**, excluding CPU/devices/temporary compilation allocations. Sources: `src/x86/jit/t32/runtime.rs:46`, `:147`; `src/x86/jit/t32/store.rs:12`; `src/x86/jit/t32/lower.rs:132`. Code-page versions additionally use 8 bytes per guest 4 KiB page (`src/x86/jit/validity.rs:106`).
Thus guest-RAM upper bounds after just the current JIT are **none / 2.19 / 10.19 MiB** on 4/8/16 MiB boards. **As-is, all three fail:** `PcVga::new()` separately allocates **16 MiB** VRAM even in the current machine construction (`src/devices/vga.rs:10`, `:122`; `src/machine.rs:2164`). Internal 512 KiB SRAM cannot cover that deficit. No DOS/Windows board boot is established.
Conditional planning budget, **unverified**: reduce VGA backing to 256 KiB, use a 2 MiB JIT arena with the existing ~1.81 MiB tables, and reserve another 2 MiB for VGA/display, other device state, SDK, stacks, allocator and I/O. Keep firmware text in NOR. The arena hook can cap supplied memory today (`src/x86/jit/t32/arena.rs:121`); VGA reduction and the complete board port remain future work. A 390×450 RGB565 buffer alone is 351,000 bytes (~0.335 MiB), calculated from the Huangshan panel dimensions in A; double buffering doubles that charge.

| pSRAM | Conditional RAM left with 2 MiB JIT + tables + 2 MiB reserve | Conservative initial guest choice; candidates, not board results |
| --- | --- | --- |
| 4 MiB | None (~1.81 MiB short) | Interpreter only: 2 MiB guest under the proposed reserve; DOS first, Windows 3.1 a minimum-memory experiment |
| 8 MiB | ~2.19 MiB | 2 MiB guest with JIT, or 4 MiB interpreter; DOS/Windows 3.1. Windows 95 only fits the 4 MiB interpreter budget here |
| 16 MiB | ~10.19 MiB | Start at 8 MiB guest with JIT; DOS/Windows 3.1/Windows 95 are memory candidates |

Windows comparison: Microsoft's historical table gives Windows 3.1 2/4 MB minimum/recommended, Windows 95 4/8 MB ([Raymond Chen](https://devblogs.microsoft.com/oldnewthing/20120102-00/?p=8743)); this establishes a memory target, not SF32 performance or compatibility. NAND variants lose additional RAM to loaded firmware. DOS and much Windows 3.1 code receive no T32 acceleration because 16-bit CS and VM86 are interpreter paths (`src/x86/jit/t32/runtime.rs:505`; `AGENTS.md`, JIT focus).

First board measurements proposed by Intern, in dependency order (no measurements performed):
1. Identify board/part/revision and boot images; report actual clocks, memory size, MPU/cache configuration, CONTROL/security state; verify pSRAM capacity and cold boot before allocating a heap. These resolve the unknowns in A–D.
2. Exercise generate/execute/overwrite/execute in the intended pSRAM region, crossing cache lines, with caches enabled; include DMA/display traffic and range maintenance. Compare to SRAM execution. This resolves the publish/alias/coherence risks in B; QEMU is insufficient evidence (`cortex-m/firmware/runtime.rs:72`).
3. Measure linked code/data, stack and allocator peaks, JIT metadata/arena occupancy and code churn; confirm the conditional E budget before a guest boot. Measure pSRAM random access and sustained instruction throughput under simultaneous display refresh and sector I/O; interface MHz is not application throughput (B/E sources).
4. Verify synchronous SPI card reads and guest media integrity, physical keys/touch and scaled framebuffer output; then compare interpreter/JIT on the same frozen guest image. Measure DOS first, Windows 3.1 next, Windows 95 only after an adequate RAM budget; do not infer M33 performance from Pi/QEMU. Storage wiring, small panels and mixed 16/32-bit execution are the risks established in A/C/E.
